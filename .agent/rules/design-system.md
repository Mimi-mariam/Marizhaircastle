# Design System Rules — Marizhaircastle

> **Relationship to AGENTS.md / tokens:** This file operationalizes AGENTS.md §10 for visual design. **Keep it in sync with AGENTS.md whenever either changes**; AGENTS.md is the source of truth. Design tokens live in **`tokens/design-tokens.css`** (generated by `tokens/convert-tokens.js` from the JSON sources in `tokens/`) — import that file once globally, and reference its CSS variables from components. If the token file changes, regenerate it and re-check this file's guidance still matches.

## Brand Feel

The interface must consistently feel:

- Premium
- Elegant
- Modern
- Trustworthy
- Clean
- Approachable

Do not introduce visual styles, components, or patterns that don't match the existing Marizhaircastle design system. When in doubt, match what already exists rather than inventing something new.

---

## Mobile-First

Marizhaircastle customers are primarily on mobile. Every component must be built mobile-first:

- Default styles target mobile (small screens).
- Use `@media (min-width: 768px)` to layer in desktop/tablet styles — never the reverse.
- Touch targets must be a minimum of `44px` tall.
- The checkout page must be fully functional and legible on a `375px` viewport.
- Support mobile, tablet, and desktop, but mobile is the primary experience and the one to validate first.

---

## Spacing

- Use multiples of `4px` for all spacing (`margin`, `padding`, `gap`). No arbitrary values.
- Allowed spacing values only: `4px`, `8px`, `12px`, `16px`, `24px`, `32px`, `48px`, `64px`.

---

## Border Radius

Use only these values:

| Use case | Radius |
|---|---|
| Small elements (badges, tags) | `4px` |
| Buttons and inputs | `8px` |
| Cards and modals | `12px` |

- Restrict component usage to `--radius-sm` / `--radius-md` / `--radius-lg` only.
- Do not use `--radius-2xl`, `--radius-3xl`, or `--radius-full` in components, even though the underlying token scale defines them. If a design genuinely calls for a value outside this set, flag it and confirm before using — don't reach for an unlisted token to solve a one-off case.

---

## Styling Method

- All component styles use **CSS Modules** (`.module.css` files), co-located with their component.
- No inline `style={{}}` props except for truly dynamic values that cannot be expressed in CSS (e.g. a progress-bar width driven by a runtime number).
- No Tailwind. No styled-components. **CSS Modules only.**
- Use design tokens (CSS variables from `tokens/design-tokens.css`) for colors, spacing, and radius rather than hardcoded values.

---

## Dark Mode

- The dark palette is activated by the `[data-theme="dark"]` attribute on the root element (see the generated `tokens/design-tokens.css`). Apply it via a documented theme toggle, `prefers-color-scheme` media query, or a root-level class/attribute — pick one mechanism and use it consistently.
- Components reference the **role variables** (e.g. `--surface-color`, `--on-surface-color`) rather than hardcoded colors, so they adapt automatically when the theme flips. Do not hardcode colors to make a component "dark-specific."
- If a dark-role value is missing, unreadable, or a placeholder in `tokens/design-tokens.css`, treat the source tokens as broken and fix them (then regenerate) — never override with a hardcoded component color to mask it.
- Both light and dark themes must satisfy the contrast and accessibility rules below.

---

## Typography & Visual Hierarchy

- Maintain consistent typography scale, weight, and color usage as defined by the existing design tokens.
- Use clear visual hierarchy to guide the customer through discovery → evaluation → purchase, and the admin through scanning dashboard data quickly.
- Product imagery is central to trust and conversion — prioritize strong, consistent product photo presentation over decorative UI elements.

---

## Interaction States

Every meaningful interaction must handle all of the following, where applicable:

- **Loading** — clearly communicate the system is processing.
- **Empty** — explain what's empty and offer a next action (e.g. empty cart → "browse products").
- **Success** — clearly confirm completion.
- **Error** — explain the problem in plain language and offer a recovery path.
- **Disabled** — visually distinct from active/enabled state.

Never show a false success state. Never fail silently.

---

## Accessibility

- Use semantic HTML as the default, not divs-with-handlers.
- All interactive elements must be keyboard-navigable with visible focus states.
- Forms need proper labels and clear, specific error messages (not just a red border).
- Maintain sufficient color contrast; never use color alone to communicate status (e.g. pair a red error state with an icon/text, not just red text).
- Images need meaningful alt text; decorative images use empty alt attributes.
- Screen-reader compatibility is required for all customer-facing and admin flows, not just a subset.

---

## Checkout & Cart UX Priorities

- Minimize steps and cognitive load above all else — every added field or click in checkout has a direct conversion cost.
- Order summary must always be visible/accessible during checkout (products, variants, quantities, subtotal, delivery fee where applicable, total).
- Communicate the 24-hour delivery promise clearly at relevant touchpoints: product page, checkout, order confirmation, order tracking.
- Cart and checkout must degrade gracefully when inventory or pricing changes mid-flow — show a clear message, don't let the customer proceed on stale data.
